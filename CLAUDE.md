# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Raahi Beats is a MERN-stack music streaming site (browse/stream songs, artists, playlists, liked songs, and real-time 1:1 chat). It was built as a college project and is now being refactored toward industry-standard code quality — see the "Known Issues / Refactor Backlog" section below for the active punch list, and `docs/frontend-optimization-backlog.md` for the more detailed frontend-specific performance/smoothness backlog (re-render/memoization, effect hygiene, asset loading).

## Commands

Run from the repo root unless noted.

```bash
npm install               # backend deps
npm run client-install    # frontend deps (client/)

npm run server            # backend, nodemon, reads .env, listens on PORT or 8000
npm run client            # frontend, react-scripts start, http://localhost:3000

npm start                 # backend only, no nodemon (production-style)
npm run client-build      # frontend production build → client/build
```

There is no test suite in either package (`npm test` in both `package.json`s is a placeholder/CRA default). There is no lint config in the root package; the client only has the default CRA `eslintConfig: { extends: ["react-app", "react-app/jest"] }` in `client/package.json`.

### Environment variables

Root `.env` (not committed, must be created manually per the README): `MONGO_URI`, `JWT_SECRET_KEY`, `PORT` (defaults to 8000), `NODE_ENV` (gates cookie `secure`/`sameSite` flags — see below).

**As of 2026-07-27, `client/.env` is a generated file — do not hand-edit it.** The root `.env` is now the single authored source of truth for `REACT_APP_HOST` (and any future `REACT_APP_*` var). `scripts/sync-client-env.js` reads `process.env` (loading the root `.env` via `dotenv` if present — a no-op if it isn't), filters for `REACT_APP_*`-prefixed keys, and writes just those into `client/.env`. It's wired into `client/package.json`'s `prestart` and `prebuild` hooks, so it runs automatically before `npm run client` and `npm run client-build`; it can also be run manually via `npm run sync-client-env` from the root. This solves two problems: CRA (`react-scripts`) only ever reads `.env` files from its own project root (`client/`), never a parent directory, and `REACT_APP_*` vars are inlined into the bundle at *build* time, not read at runtime — so this has to run before every client build, not just once. On Render, since dashboard-configured env vars are injected directly into `process.env` for the build step (no physical `.env` file needed there), the same script works unmodified — **provided `REACT_APP_HOST` is set in that Render service's dashboard**, which has not yet been confirmed/set as of this note.

`client/.env` **is still committed to git** with the production URL as of this note (see the backlog decision below) — but because it's now a build artifact regenerated by the sync script on every local `npm run client`/`client-build`, there is a real risk of accidentally committing a localhost value over the production one after local dev. Once `REACT_APP_HOST` is confirmed set in Render's dashboard, `client/.env` should be `git rm --cached` and added to `.gitignore` — it no longer needs to be hand-maintained or committed at all.

MongoDB database name is hardcoded in `index.js`: `mongoose.connect(`${process.env.MONGO_URI}/raahi-beats-mern`)`.

## Architecture

### Backend (repo root)

Express app in `index.js`. No controller/service layer despite the README's documented folder structure claiming one — route handlers in `routes/*.js` contain the Mongoose queries and business logic directly.

- `routes/` — one router per resource: `UsersRoute` (signup/login/logout), `SongsRoute`, `ArtistsRoute`, `PlaylistRoute`, `ChatsRoute` (contacts + message history), `UtilsRoute` (share-link/short-link generation, device-details ping).
- `models/` — Mongoose schemas: `UserSchema`, `SongSchema`, `ArtistSchema`, `PlaylistSchema`, `ChatSchema`, `ContactsSchema`.
- `middlewares/` — `decodeToken.js` (JWT cookie → `req.user`, applied selectively per-route, not globally), `multer.js` (song/artist file storage), `UserFileUpload.js` (avatar upload).
- `websocket/chatWebsocket.js` — Socket.IO server mounted at namespace `/api/chatnamespace`, handles `register` (bind socket id to a `ChatSchema` doc by user email) and `private-message` (persists to both sender's and receiver's `ChatSchema` doc, relays live if the receiver's socket is known).
- `Utils/DeleteFile.js` — cleans up uploaded files when a request fails partway through.
- `uploads/` — local disk storage for song/artist/user media, served statically at `/api/uploads`. **This directory is committed to git** (252 binary files) — there is no `.gitignore` in the repo at all.

**Data model quirks to know before touching schemas**: Songs/Artists cross-reference each other by embedding `{_id, name}` pairs rather than using Mongoose `populate` (population would break anyway — `ArtistSchema.songs` sets `ref: "Songs"` and `ChatSchema.user` sets `ref: "Users"`, but the actual registered model names are singular `"Song"`/`"User"`). Route handlers re-fetch and re-embed data manually (`JSON.parse(JSON.stringify(doc))` is the dominant pattern for turning a Mongoose doc into a plain object across almost every route, instead of `.lean()`). "Liked" status for a song/artist is computed per-request by decoding an optional `userToken` from the request body and cross-checking `User.favourites` — this logic is duplicated near-verbatim across `SongsRoute`, `PlaylistRoute`.

**Auth model**: JWT signed with `JWT_SECRET_KEY`, stored in a cookie named `token` (plus a separate non-httpOnly `user` cookie holding `{username, avatar}` JSON for the client to read directly). `decodeToken` middleware is applied only to routes that need a known user (playlists, contacts/chat) — song/artist add/delete routes currently have no auth middleware at all.

### Frontend (`client/`)

Create React App, plain JS/JSX (no TypeScript), React Router v6, Socket.IO client. No Redux/Zustand/React Query — state is React Context + `useState`/`useRef` only.

- `src/App.js` — single entry point; wraps the whole tree in six nested context providers (`AlertState > AuthenticationState > SongState > AudioState > ArtistState > PlaylistState > ShareState`), then renders `Navbar`, `SideNav`, the route table, and always-mounted overlays (`BottomControls`, `FullScreen`, `ShareDialogue`, `PlaylistDialogue`). Only `/chat` is wrapped in `ProtectedRoute`; other "must be logged in" checks happen ad hoc inside context methods via `Cookies.get("token")`.
- `src/Context/{Alert,Artists,Audio,Authentication,Playlist,Share,Songs}/` — one Context + `*State.js` provider per domain. Every provider makes its own raw `fetch` calls directly against `process.env.REACT_APP_HOST` (no shared API client). `AudioState` is the largest and most central: it owns the actual `Audio` element, queue, play/pause/seek/shuffle/loop logic, and also reports play/like counts back through `SongContext`.
- `src/Components/` — organized by feature/page (`Home`, `Artists`, `PlaylistPage`, `PlaylistDialogue`, `ChatApplication`, `ControlArea` (the persistent bottom player bar), `FullScreen` (expanded now-playing view), `SearchPage`, `SongDetailsPage`, `Authentication`, `Navbar`, `SideNav`, `Queue`, `LikedSongsPage`, `ShareDialgoue` (sic)).
- Auth/user sync between `Navbar` and `AuthenticationState` uses a manual `window.dispatchEvent(new Event("cookies"))` pub/sub hack rather than shared state, because the user's identity isn't centrally held in context.
- `react-beautiful-dnd` (used in `Queue.jsx` and `PlaylistDialogue/CurrPlaylist.jsx` for drag-to-reorder) is deprecated/unmaintained upstream.

### Real-time chat

Chat is entirely separate from the REST API's `ChatsRoute` (which only reads history/contacts) — live delivery goes through `websocket/chatWebsocket.js`. A `ChatSchema` document is keyed by `email`, not user id, and does double duty as both "a user's own chat log" and "an ad hoc contact record" depending on which code path created it — read both `ChatsRoute.js` and `chatWebsocket.js` together before changing message persistence, the logic is easy to break silently.

## Known Issues / Refactor Backlog

Captured from a full-codebase read on 2026-07-27, before any refactor work started. Verify an item still applies before acting on it — this list will drift as refactoring proceeds.

**Security / correctness (highest priority):**
- Auth cookie (`token`) is set with `httpOnly: false` in `UsersRoute.js` — readable/stealable via JS, defeats the point of an httpOnly session cookie.
- `SongsRoute` and `ArtistsRoute` add/delete endpoints have no auth middleware — anyone can create/delete songs and artists without logging in.
- `SongsRoute.js`'s root `POST /` handler (list/search songs) has no top-level `try/catch`; an invalid `userToken` will throw inside `JWT.verify` uncaught.
- No rate limiting anywhere (login is brute-forceable), no CSRF protection despite cookie-based auth, no `helmet`.
- The error-handling middleware in `index.js` is registered *before* the routes — Express error middleware only catches errors from handlers registered earlier, so this one currently catches nothing. Per-route error middlewares in `UsersRoute.js`/`ChatsRoute.js` are similarly dead since handlers never call `next(err)`.
- `ChatsRoute.js` builds its router with `express()` (a full app instance) instead of `express.Router()`.
- Mongoose `ref` name mismatches: `ArtistSchema.songs[]` refs `"Songs"` (registered model is `"Song"`); `ChatSchema.user` refs `"Users"` (registered model is `"User"`) — `populate()` would silently fail if ever used.

**Repo hygiene:**
- ~~No `.gitignore` anywhere in the repo.~~ Fixed 2026-07-27: root `.gitignore` added (covers `.env`, `node_modules/`, `client/build/`, logs, OS/editor cruft). It only prevents *future* accidental commits — it does not untrack anything already in git.
- `uploads/` (252 binary media files) and `client/.env` are still committed to git (pre-existing, unaffected by the `.gitignore` addition).
  - ~~`client/.env` was deliberately re-tracked...~~ **Resolved 2026-07-27**: `scripts/sync-client-env.js` (see "Environment variables" above) now regenerates `client/.env` from `REACT_APP_*` vars in `process.env` on every `prestart`/`prebuild`, so the file no longer needs to be hand-maintained or committed. Rahul confirmed `REACT_APP_HOST` is set in the Render service's dashboard, so `client/.env` was `git rm --cached` and is now covered by `.gitignore`. It still exists on disk locally (regenerated, gitignored) — this is expected, not a leak.
  - `uploads/` being committed is still an open decision — not yet discussed with Rahul.
- Self-ping keep-alive hack in `index.js` (`setInterval` hitting the prod Render URl every 15 min) — a hosting-tier workaround baked into application code.

**Backend structure:**
- No controller/service/repository layering — all logic lives in route handlers.
- Pervasive `JSON.parse(JSON.stringify(doc))` instead of Mongoose `.lean()`/`.toObject()`.
- "Liked" status computation duplicated across `SongsRoute` and `PlaylistRoute`.
- No centralized logger (raw `console.log`/`console.error` throughout), no request validation library (manual regex checks inline), inconsistent response shapes (`error` vs `message` fields vary by route).
- `shortid` package (used for slug generation) is deprecated upstream — candidate for replacing with `nanoid`.
- No tests, no CI.

**Frontend structure:**
- No API/service layer — raw `fetch` duplicated across every Context provider and some components directly (e.g. `ChatArea.jsx`, `ContactsArea.jsx`).
- No centralized user/auth state — components read `Cookies.get("token")`/`Cookies.get("user")` ad hoc; synced via a manual `window.dispatchEvent(new Event("cookies"))` hack in `Navbar.jsx`.
- ~12 components duplicate an identical "read `.navbar` offsetHeight" `useEffect`; the `window.innerWidth < 1000` mobile breakpoint is hardcoded independently in 5+ files.
- `AudioState`'s context value is a large object rebuilt every render with no `useMemo`; consumers aren't wrapped in `React.memo`, so most player-adjacent components re-render on any playback state change.
- Commented-out dead code left in place in `Seekbar.jsx`, `SongDetailsPage.jsx`, `FullScreen.jsx`, `HomePage.jsx`.
- Inconsistent error/loading UX: a mix of `showAlert()`, raw `alert()`, and `console.log`, and loading states are just literal `"Loading..."` text with no shared component; no error boundaries anywhere.
- `react-beautiful-dnd` is unmaintained (used for drag-reorder in `Queue.jsx`, `CurrPlaylist.jsx`).
- Media URLs are built by hand-concatenating `${host}/${path}` throughout instead of a shared helper; `AudioState` manually `.replace(/\\/g, "/")`s Windows-style paths coming from the backend, i.e. a backend path-format problem leaking into frontend code.
